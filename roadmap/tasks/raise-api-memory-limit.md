# Поднять лимиты памяти API в проде (raise-api-memory-limit)

- **Пункт ТЗ:** вне ROT/GEN — эксплуатация, по итогам мониторинга VPS 01.10.2026
- **Ветка:** `feature/raise-api-memory-limit`
- **Базовая ветка:** `master` (открытых PR нет)
- **PR:** #<номер> (после создания)
- **Статус:** 🚧 In progress

## Контекст

Мониторинг прод-VPS 01.10.2026 (4 часа, сэмплы cgroup раз в минуту) показал, что приватный API
(`genesysforge-api`) за вечер живой игровой сессии вырос с 256 до 284 МБ при `mem_limit: 320m`
(пик 290 МБ), и к 03.10 часть его памяти ушла в swap. Около 105 МБ — `shmem`, вероятно двойное
отображение JIT-кода (W^X). .NET в контейнере по умолчанию ограничивает кучу 75% лимита cgroup,
то есть при 320m на неё оставалось ~240 МБ. OOM-событий пока не было.

Владелец выводит из эксплуатации beauty-study (освобождается ~480 МБ RAM), поэтому поднимаем
потолки GenesysForge. Затрагивается только `docker-compose.prod.yml`; код, схема БД и API не меняются.

## План выполнения

- [x] `api`: `mem_limit` 320m → 512m
- [x] `api-public`: `mem_limit` 320m → 384m (трафика почти нет, ~170 МБ)
- [x] `docker compose -f docker-compose.prod.yml config` разбирается
- [ ] PR открыт
- [ ] После мержа и деплоя: `memory.max` у контейнеров 512m/384m, `/api/health` отвечает 200

## Что осталось / блокеры

- Мерж = прод-деплой: пересоздаются `api`, `api-public`, `web*`, а из-за плавающего тега
  `postgres:17-alpine` при выходе нового патча перезапустятся и БД. Время мержа выбирает владелец.
- До мержа лимит можно поднять на работающем контейнере (`docker update --memory 512m
  --memory-swap 1g genesysforge-api`, под root). Лимит кучи .NET при этом пересчитается
  только после рестарта, то есть после деплоя.

## Заметки / решения

- Тесты не нужны: меняется только конфигурация деплоя (AGENTS.md — тестовые требования не затронуты).
- Не делали: `DOTNET_EnableWriteXorExecute=0` (меньше shmem и быстрее старт) и закрепление тега
  `postgres` — отдельные решения, вынесены в отчёт мониторинга.
